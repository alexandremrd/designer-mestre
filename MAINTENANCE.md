# Skill maintenance

Read only when changing, installing, or publishing the skill (formerly §7 of `SKILL.md`, the maintenance part). It adds no weight to piece requests.

## 7. Shared source, changing the agent, and publishing
- **Check before deleting or publishing:** clean up only temporaries created in the session that nothing references (preview, export script, HTML); publish = push to the remote's default branch, after checking `git status -sb`. **Before publishing or calling an edit done, run `python assets\verify_package.py` (checks the package for Git): it blocks client names (read from the folders of `D:\Clientes`, without storing any in the skill), a generated file inside the package, a date inside a rule, a Law that is too long, and a `.gitignore` that hides the client template.** Failed = do not publish.
- **Root before rule:** when reviewing a failure, read the critique and the available artifacts/outputs and follow the real flow to the responsible function. Record the mechanism that caused the error before choosing between fixing, reusing, or routing; do not create a parallel capability to work around an existing module.
- **Integration conflict = user's decision:** when integrating a reference, method, engine, or format, if there are incompatible instructions or alternatives with a material trade-off, do not choose on your own nor delete a capability. Stop only at that point and present the decision in `ask_user`, with a short question and comparable options (choice boxes), a recommendation indicated when there is evidence; state the consequence of each option. Wait for the answer before implementing the conflicting part; keep going on the independent work. Distinguish a real conflict from complementary options: when they coexist without cost or contradiction, integrate them without interrupting.
- **Shared source:** a single physical folder at `D:\Documentos\Skills\Designer Mestre\Arquivos`, reachable through junctions in the local AIs. A change authorized through any of those paths edits the same source immediately, with no password or copy synchronization. Before converting an old installation, reconcile exclusive changes by content. `Installer.ps1 -Sim` checks/creates the links and shortcuts, without copying the skill nor publishing. Installing in another local AI automatically reuses the registered source; on another computer, register a single source at the first installation, without presuming D: nor this machine's paths. This guideline ships with the package and holds even without Aprenda active. Cloud-managed caches never receive a writable link to the source. Update version, README/Changelog, and EVOLUTION (current + four previous, dropping the oldest); check the accesses and reload instructions in the AIs when necessary. Publish to the `origin` remote only on explicit request; a remote conflict or unavailability blocks only that step. Checking the files does not prove activation in each runtime. **Resources and skills:** a downloaded or installed resource (tool, model, engine, cache) lives only in `D:\Recursos IA`, registered by `designer-mestre\assets\resources.py` (finds tools and models in the resource root); an imported skill or engine enters only the central source `D:\Documentos\Skills`, a fixed location that is neither changed nor duplicated (nothing in `~/.claude/skills/*`, `~/.cache`, or `C:`).
- **Changing the agent:** first read `EVOLUTION.md` and build a short map of the requested capability against the core, routes, modules, scripts, available tools, and relevant specialist skills. Classify each function as covered, partial, or gap; locate duplicates by result/inputs/outputs, not by title. Reuse the covered function; adapt the partial function in the file that already has it; create a new capability only when the gap is demonstrated. For overlapping functions, synthesize one entry point + common rules + routes for exclusive variants; do not concatenate whole documents, delete distinct expertise, or mix deliverables with different authorities. Confirm that old triggers and consuming flows remain routed. Evaluate tokens/time together with observable quality. A universal rule enters the core or the owning module, replacing the old one; a value that holds for 2+ modules enters `standards.md` and the modules cite `U#`; a new file only if it is an on-demand attachment of §1. Validate with reuse cases, synthesis with a variant, and separation of specialties. Afterwards: update `EVOLUTION.md` (replace, do not stack) and 1 line in the Changelog of `README.md`. **Keep the change in the source only until the user's explicit approval; only then run `Installer.cmd` and check the installed copies.**
- **Laws and rules:** a Law is a short, universal principle: no client name, date, measure, or case. Procedure, measure, and exception go to the owning module (the Law points to it); the episode that motivated the rule stays only in `EVOLUTION.md`, described by its cause, never by the client. A client's learning stays in their `_DESIGN\`.
- **Pending items:** every postponed decision, missing test, or item that depends on the user becomes a line `- [ ] YYYY-MM-DD · priority · item · who decides` (priority is `high`, `medium`, or `low`; who is `user` or `agent`) at the end of `EVOLUTION.md`; when resolved, `[x]` and the date. It is what `assets\skill_alerts.py` counts and shows at the end of the session, after the final approval of the tasks: what is not on this list does not reach the user.
