# Delivery · cycle, proof, wrap-up, names, folders, and memory

Read before producing or delivering any visual piece (formerly §2 and §7 of `SKILL.md`). The routes, the Laws, and the KV Gate live in `SKILL.md`; the `U#` standards live in `standards.md`.

## 2. Delivery cycle (single; modules do not repeat it)
- **Mechanical** (captions, resize, swap text/color, export, adjustment in an existing file or Figma): execute directly; v1 is the delivery. Cutting or assembling the speech of a video is not mechanical: it decides rhythm and meaning, so it follows the cut plan in `video.md` §2.3.
- **New creative:** with a validated KV, start from the approved template or client template of the format (`_DESIGN\templates\`) and from the last approved deliverable of the same format, swapping copy and photo and preserving positions, typography, and layers; design from scratch only what they do not cover, because a layout invented outside the standard is the most repeated cause of rejection. Without an approved template, start from an idea and choose the engine and workbench combination with the greatest creative power suited to the concept, render/preview quality, and editing capability among the available tools. The choice is for the best possible result, not for a prior preference for SVG or for an export format. HTML/CSS/JS with preview in the Browser canvas, SVG, native Figma when requested/available, Python/PPTX, raster, or hybrid composition are possible means, not a hierarchy nor presumed delivery formats. The workbench can be an interactive page/tab with canvas, useful controls, and visual updating; do not call it Figma or the final file. Explore and iterate with the user in that visualization; do not export the final package before approval, unless there is an explicit request for direct delivery or a mechanical flow. The format/channel described in the briefing informs the composition, but does not force the final file extension. After approval, if the extension and final standards have not yet been indicated, ask which file, size/profile, and export standard they want; respect the preference already recorded for that client when there is one. Then export and deliver only the chosen formats.
- **Export gate:** nothing goes into `Exportados\` before the yes to the preview in `Aprovação\`; the rejected version leaves the folder when the new one enters.
- **Preview and iteration:** at each visual step, update the workbench in use and present the current version; prioritize an updatable interactive preview if available. Otherwise, generate a capture/raster and show it. A preview does not imply a saved final file. Receive feedback and iterate without an arbitrary limit of rounds as long as each pass makes progress; stop if a decision is missing, if the tool blocks, if the change goes out of scope, or if new attempts do not change the problem. The generated image may be shown as working material, but that does not oblige exporting the piece. Every preview, variation, or file cited is delivered as in the `Localização:` of the wrap-up. A rejected preview is deleted when the new version replaces it, so the folder does not accumulate dead versions; an AI-generated image is not deleted (it stays in `IA\` with the `.txt`). The preview is self-sufficient (logo, images, and local fonts embedded in inline SVG or data URI), because the user may open it in a viewer without access to the folder; check in the same viewer they will use, not only in the automatic render.
- **Proof before claiming** (every delivery; the user is not the QA): (1) before showing, compare the changed region at full size, side by side with the source or the approved reference; a visible deviation gets corrected, and a caveat is left only for what the inputs do not allow correcting; (2) before saying an input is missing (photo, logo, font, copy), search the client's folders, the official sources, and the original file at the origin, judging by content, not by name or quantity; (3) two attempts failed = measure the output (numbers, crop, difference) before the third, abandon the approach that got worse, and offer the user the alternative exits from `references\alternatives.md` (they choose; consecutive failures or errors are the trigger); (4) a new version does not replace a reusable approved asset (package, template, design system, exported file) before it is approved; (5) after exporting, check the decoded final file, not the preview (`quality.md` §K); (6) check the quality tier and processor actually used (U13), from the log, and not by assumption.
- **Per-unit correction cycle** (every delivery; it is the `/360-product` cycle written for each type): correcting well depends on five things together, not on "having a checklist".
  1. **Isolable unit:** every delivery divides into units that can be redone on their own (table below). Define them **before** producing and number them.
  2. **Source of truth with hierarchy:** each unit is checked against the best source of its type; a lower source only fills gaps and never contradicts the higher one; what was inferred is marked and kept separate from what was observed, and visual approval does not prove an inferred detail.
  3. **Check board:** before showing, assemble a numbered board with **Source | Result** on the same crop and at full size (the one the user sees is the same crop, with the unit number). The defect shows up on the board, not in reading the code or the list.
  4. **Named cause and accumulating rule:** on rejection, state the layer and the cause (weak source, prompt, geometry, tool, copy, step order) and record **1 short corrective rule** in the project checklist (`PRODUTO_*.md`, `PERSONAGEM_*.md`, or `Trabalho\checklist.md`); it enters the next units **before** producing. At the end, what holds for the client goes to `_DESIGN\guia.md` (`## Reprovado`) and what holds for everyone, only as a principle, goes to the skill.
  5. **Granular feedback and redo:** the user approves the set **or points out just one unit**. If one is rejected: go back to the source **only for that one**, fix the cause, and replace only it; never redo the whole piece nor touch the approved units. A new version only replaces an approved asset after it is approved.
  Complements: **gate before spending** (check that the session's tool supports what the method requires, such as a generator with image reference, and if it does not, stop and say what unlocks it, without degrading silently); **two attempts without improvement = measure the output** before the third, abandon the approach that got worse, and offer `references\alternatives.md` (proof 3); states **under evaluation, approved, incorporated into the collection**, and nothing becomes a reusable asset before it is approved.

  | Static ad or post | layer or region (title, photo, logo, badge, background) | briefing + literal copy + KV + approved template of the format | piece × template or approved reference, numbered regions | `quality.md` A, H, E, I | `check_image.py board` and `contrast` |

- Ask only what blocks the direction, the identity, compliance, or a material production decision; do not interrupt exploration to decide the export extension.
- Adjustments during iteration must respond to the feedback and act on the relevant layer (in self-correction, adjust the element's position, timing, or scale before deleting it), but they need not be atomic nor respect a fixed ceiling when the composition calls for a broad change.
- A working file may exist to feed the preview; distinguish it from the final file. After approval, export only the chosen formats and save the complete result at the agreed destination.
- Wrap-up. **Trigger:** any reply that cites a task, piece, or creative delivery uses the block, including the reply of `/aprenda` and the report of a skill change (the skill part continues in running text, without this pattern). The block carries no headings, lists, or tables, only the lines below; the mention goes in its own block, never in a loose sentence; the ⏸/✅ line also cites each pending delivery by the block's name: one block per delivery of the round (each piece is a delivery: static, video, deck), so the user knows at a glance what is on them. Each block carries only the context, files, and request of that delivery; nothing from one delivery appears inside another. No labels, except `Localização:`, in this order and one part per line: task name in bold · emoji + status word chosen by context (e.g.: ✅ Ready, 👀 For approval, ⚠️ Needs your attention, 🛑 Blocked) · the essential context, with assumptions and gaps · what blocks, if anything · `Localização:` the folder of the round's deliveries and one item per file (preview, final, generated image, including those outside the folder), in the format the current agent opens. Identify the environment by the available tools and use its native mechanism: attach/show the file in the conversation, reveal in the explorer with the file selected, or `file:///` link where the chat opens local links; a markdown link with an absolute path does not open in every client. Always include the full folder path in a code block, to copy. The file items do not replace the folder. A delivery that stayed outside the client's folder (`D:\Clientes\[Client]\...\Aprovação`) is flagged in `Localização:` and copied into it. The reply that confirms approval or export opens with this block, with the full folder in a code block; questions and pending items come after.
  The last line of the reply, outside the blocks, carries only an emoji and one word of the current state, in bold: **⏳ Exporting**, **⏸ Paused** or **✅ Done**; the pending decision goes in the previous sentence. Uploading files to Drive or the client's delivery folder is a user step, not the agent's: it is not a pending item nor a blocker, and a piece approved and saved in `Exportados\` closes with ✅ (cite the destination folder only as information). Optional offers come before it, never in its place. Before a long step (render, transcription, download, installation), warn in 1 line what will run, so the wait does not look like a freeze. A technical choice (engine, format, method, alternative with trade-off) always goes through the question tool, with options; approval of a piece may be answered by text. Include Three.js when 3D contributes to the concept; if an engine fails or does not meet the result, suggest verified equivalent alternatives, explaining visual gain, inputs, and export limits, without silently switching the required method. Check whether the capability is already available; install or download dependencies only when necessary, with a one-time approval recorded per capability per `operations.md` §0.6; the question first states, in plain language: what the tool does, where and how the skill uses it (module and step), size, license or cost, and the destination in `D:\Recursos IA`; a failure does not authorize installation nor extra spending. An explicit request for an engine already settles its choice. No narrating reading.
- Opening the folder: on the first delivery for approval, if `consent.py view preferencia.abrir_pasta` has no answer, ask once whether the user wants the AI, at each preview for approval and each final approval, to open the explorer at `Aprovação\` (previews) or `Exportados\` (finals) with the file to evaluate selected, never at `Trabalho\`; record the answer with `consent.py register preferencia.abrir_pasta --note sim|nao` and follow the note from then on, in every AI.

- **Workbench and final format (procedure of Law 6, full text):** for each piece, choose the combination of engine and creation/preview medium with the greatest creative power suited to the concept and the available tools. SVG is a vector option, not a universal requirement nor a presumed starting point; HTML/CSS can be a visual workbench, Python/PPTX can serve editable presentation documents when the environment allows, and native/Figma formats are used when requested. An HTML preview does not change the sites route rule: LP, site, and slides are delivered as pixel-perfect HTML, a single file with no framework or build (`html.md` §1), checked against the reference/briefing and tested in the needed viewports. React, Vite, Tailwind, bundlers, and similar only come in as a suggestion (`references\alternatives.md`) when the case calls for state, an app, or a client project already on that stack, and never replace this delivery without the user's yes.
  - **Authoring and editable export:** HTML/CSS on a fixed artboard is an option for statics, with no reflow at the output size; direct SVG favors maps/diagrams and vector editing. Plan the requested editable format from authoring onward: arbitrary HTML does not automatically become native SVG. `foreignObject` keeps HTML, and embedded raster does not gain vector editability. Preserve the HTML/CSS or native source and declare rasterized layers; confirm parity at the editing destination when available. Details in `ads.md` §4.

## 7. Naming, folders, and memory
- **Naming of upcoming deliveries:** use `<Delivery> #<order in the copy> - <Type> - <width>x<height>`; in a sequence of cards, append ` - <card order>`. Examples: `Entrega #1 - Carrossel - 1080x1350 - 1`, `Entrega #2 - Reels - 1080x1920`, `Entrega #3 - Stories Estático - 1080x1920`. The numbering identifies the delivery in the copy within the task, not the export order; cards and adaptations of the same delivery keep the number. Apply to presented names, delivery frames, and files (extension at the end); a revision keeps the base and appends `_V2`. Do not rename existing deliveries retroactively; continue the upcoming ones in the same pattern. Preserve the task's original name in the folder. For formats without a fixed pixel dimension, use the pertinent size without inventing measures.
- Folder: `[AAAA]\[MM - Mês]\[AAAA-MM-DD] [TIPO] Título\` with `Referências\`, `Trabalho\`, `Aprovação\`, `Exportados\` (types CA PA EV MT LP KV DK IM OT). `Aprovação\` holds only the round's piece in the format in which the user evaluates it, with version suffix: motion/video = the self-sufficient HTML preview that plays with audio (no rendering MP4 before approval); static = the piece's image. Scene screenshots, board, scripts, and sources stay in `Trabalho\`, because they serve the AI's checking, not the approval; a piece created for a project (program, artwork, audio) stays in the delivery folder (`Trabalho\`), and, if it serves any project, check in the skill where it fits and store it together with its similar ones (e.g.: `assets\`); a rejected preview leaves when the new one replaces it; Title = the task name as the user sent it (not the copy's theme), so they find the folder by the same name; the user's folder wins; revisions `_V2`. When exporting the finals, open `Exportados\` with the main file selected if the folder-opening preference (§2) is `sim`.
- Memory: **1 write at the end**. The client's approved and rejected → `_DESIGN\guia.md`, as brief suggestions ("Aprovado" / "Reprovado"), with the skeleton in `templates\` and the winning recipe in 1 line; color/font/logo → `design_system.md` `## 3. KV`; business → `## 4. Inteligência`. What holds for any client → the agent's `GUIDE.md`. Merge instead of stacking; ceilings ~1.5 KB per guide and ~6 KB in `design_system.md`. Date: 1 line in `historico.md`. At the end of each project, offer `/aprenda` to rewrite the two guides and trim from the core what became a suggestion.
- Universal technical bug: fix, record in the client, ask in 1 line whether it becomes a general rule.
- **Client photos and assets (procedure of Law 5, full text):** `Compartilhada\` already comes separated (Identidade Visual · Imagens · Referências · Vídeos): go straight there, without sweeping folders, and work inside the client's folder. `Compartilhada\Imagens\` = `Originais\` (only real client photo, read-only) · `Banco de Imagens\` (licensed) · `Tratadas\` (derived from an original: retouch, cutout, upscale, suffix `_trat` + `.txt` with origin) · `IA\` (every generated image + `.txt`). A generated image, from any engine (including a partner AI such as Codex), is saved immediately in `IA\` + `.txt`, at the generator's original resolution, before enlarging or composing. Backgrounds or scenes created from products are a reusable asset: the asset is created and approved separately, saved in high quality in the client's folder, and only then enters the piece by the best viable method (swap the image layer in the SVG or in Figma). Order of use: `Originais\` → `Banco de Imagens\` → `Tratadas\` → `IA\` → generate (`image.md`). **A generated or treated image never enters `Originais\` nor `Banco de Imagens\`**; found out of place = move to the right folder and warn in 1 line. Text, label, and logo never in the generated image (they go in the SVG). A real person only with recorded authorization.
- **Scripts and helpers written for a delivery:** they stay in `Trabalho\` and are named `<SIGLA>_E<NN>_<function>.<extension>`: SIGLA = `Client code` from the card (`_DESIGN\mapa.md`), NN = delivery number (the same `#` as the delivery name), function = a word saying what the file does (`assemble_reels`, `exportar`, `palavras`). Use underscore, not hyphen, so Python can import it. Files the skill's scripts **read** have a fixed name and carry no sigla (`mapa.md`, `reels_script.json`, `pieces.html`), because the contract must be predictable. Nothing born in the client's folder goes up to the skill's Git: reusable templates enter `assets\` with a neutral name and no sigla.
