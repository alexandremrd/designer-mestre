# HTML module · one studio (LP, site, form, extraction, embed, report and deck)

Routes `html`, `lp`, `extract`, `embed`, `report`, `deck`. **One flow for everything that is an HTML page or presentation.** What changes between requests is the **entry profile** (§0), which turns steps on or off; the file contract, the concept, the viewports, the gates and the per-unit fix are the same. This file replaces the former `html-extrair.md`, `html-relatorio.md` and `deck.md`; nothing from them was left out.
Assets in `<AG>\assets\`: `base_lp.html` (tested base: shielding, SEO, mask, UTMs, webhook, skip-link), `base_deck.html` (optional deck base), `check_html.py` (checks the page: bytes, SEO, screens, scrolling), `check_deck.py` (checks the HTML deck), `form-validation.js` and `.css` (CPF, CNPJ, state and city) and `preview_adjustments.js` (live adjustment in the preview).

## 1. File contract: single file, anti-mojibake and shielding
**Priority:** LP, site, report and slides ship as pixel-perfect HTML, **single file**, with no framework or build (Law 6). Framework and build only as a suggestion, after consecutive failures or errors or when the client's project already uses that stack (`references\alternatives.md`). **The workbench may use separate files while editing; the preview and the delivery are always the self-contained single file.**
**Single file (builder requirement):**
- One `.html` with internal `<style>` and `<script>`. No external `.css` or `.js`, no framework, no build. Exception: Google Fonts.
- Images: large ones (photos) by absolute URL already hosted on the builder; small ones (icons, logo) as inline SVG or base64 (base64 above ~800 KB in total makes the page heavy). In deck and report, everything embedded: the user can open it without access to the folder.
- Save the final HTML in the request's `Exportados\`; working versions in `Trabalho\`.
- **Builder character ceiling:** each platform and version has its own import limit, and it can change between versions (a new one may accept less than the previous one); never assume the ceiling recorded in the client's `design_system.md` is still valid. In any HTML adjustment near the limit: all new JS and CSS goes in minified (zero comments, zero superfluous line breaks, short variable names), check the final size (bytes and characters) before redelivering and, if the builder refuses even below the known ceiling, record the new real ceiling in the client's `design_system.md`.
**Anti-mojibake:** visible content with HTML entities (`&aacute; &atilde; &ccedil; &eacute; &ecirc; &otilde; &ndash; &nbsp;`…); strings in `<script>` with Unicode escape (`ç`); CSS and JS comments in ASCII only. A page created from scratch has **zero non-ASCII bytes** (`check_html.py` checks it).
**Known layout failures:**
- **White strip between blocks:** `html,body{margin:0;padding:0}` with `background` set; `img,svg,video,iframe{display:block;max-width:100%}`; sections separated by `padding`, never by outer `margin`; first and last child of each section with margin 0; each section paints its own background.
- **Title vanishing in animation:** base state always visible in the CSS; animation only with `.js-anim` added by the JS; the H1 animates only `transform`, never starts from `opacity:0`; safety timeout that reveals everything; `prefers-reduced-motion` turns the animation off.
- **Blue outline on logo and links:** `img{border:0}`, `-webkit-tap-highlight-color:transparent`, no outline on click and `:focus-visible` visible in the brand color.
- **Builder shielding:** `*{box-sizing:border-box;margin:0;padding:0}`, `.centralizar:empty,[id^="b_"]:empty{display:none!important}`, `#site{width:100%!important;min-width:0!important}`, `[hidden]{display:none!important}`, `.form-feedback:empty{display:none!important}`.
- **Horizontal scrolling:** no fixed-width element wider than the screen; grids with `minmax(0,1fr)`.
- **Internal CTA does not scroll to the target (GreatPages-type builders):** always sync `href="#id"` with `data-bloco` and `data-bloco-mobile` pointing to the SAME id, never only the `href`: an external script (GTM, agency tracking) can intercept the click by reading `data-bloco` and ignore the `href`. Reinforce with the file's own JS: capture listener (`addEventListener(...,true)`) with `preventDefault()` and `scrollIntoView({behavior:"smooth",block:"start"})` directly on the buttons. Test the real click (hit-test, not `element.click()` via JS) in the §2 viewports before delivering.

## 2. Flow, viewports and page that does not open
**Mandatory flow (all profiles):** (1) **Top** (core §1) plus 1 line: units in order (sections or slides), objective and missing material; (2) **lock the base** before the content: color and typography tokens from `design_system.md` and spacing scale, starting from `base_lp.html` (or `base_deck.html`) on a new page; (3) **build unit by unit**, each with a single objective; (4) **run the gates** (§9) and fix until the FAILURES are zero; (5) **deliver** via `delivery.md` §2, with the list of what changed and the pending items.
**Viewports, one list only (U5):** 375 · 768 · 1024 · 1440 for everything web. A deck's fixed canvas (§8) is scaled and checked at 1024×768, 1366×768, 1600×900 and 1920×1080. The layout's own breakpoints (for example 980 and 640 in the report) are a design decision and are tested within that list, not in place of it.
**Page that does not open (login, paywall, block):** ask for the saved HTML (Ctrl+S, "complete page") or a screenshot; never guess.

## 3. Concept and argument (LP, site, report and deck)
Taste Skill method (MIT) merged into the flow. Only step 1 is essential; the rest comes in depending on the piece. It does not run on a one-off adjustment or on a piece whose composition `design_system.md` already defines. The copy follows the client's (Law 4): the method organizes and checks, it does not rewrite.
1. **Inventory:** list 8 to 12 things only this client has (the name and what it means, the address and what the place is like, the numbers in the briefing, the constraint they live with, materials and colors, rituals and schedules, printed matter from their world). This is where the idea and the image search come from.
2. **Argument:** list the page **or the deck** as claims, one per section or slide, each with its proof (image of the thing, number, name, demonstration). A section or slide without a claim goes. When the subject or the traffic temperature calls for it, the argument order replaces the LP reference order (§4).
3. **Idea:** "in this piece, [something from the subject] becomes [the visual resource]". Competitor test: put the closest competitor's name in the sentence; if it still works, the idea belongs to the category. "Clean and modern" is not an idea.
4. **One living thing** (optional): something the visitor does or that changes with each visit, made from the real content (choose the material and see the piece in it, type the name, see the installment value). Works with a thumb and has a simple version without script.
5. **Direction** (optional): `node <AG>\assets\taste\scripts\draw.mjs --sector <sector> --brief "<one line>" --sections <roles> --options 3 --out <folder>\Trabalho\direcao` draws 3 of 20 composition directions (hero, sections, typography, palette) from a library of 247 studied sites. Choose the one that carries the idea and repeat with `--direction <id>`. Use `--keep palette,type` when the KV fixes colors and fonts (the KV wins, U11). `--list sectors` and `--list roles` show the vocabulary. Set `TASTE_SKILL_HISTORY=%USERPROFILE%\.designer-mestre\taste-history.json` so the history does not land in `~\.taste-skill`. Adopt the direction without mixing it with the usual layout; swap an item (`--redraw`) only with a reason (contradicts the KV, requires an asset that does not exist). Requires Node 22+, runs locally and offline.
6. **Title:** about 32 characters fit on 2 lines on mobile at 44 px (count and forms in `references\taste\copy.md` §§2 and 3). If the client's copy exceeds that, point it out in 1 line, without rewriting.
7. **Images from open collections** (optional, with one-time approval: `consent.py register assets_abertos` (records and queries the user's one-time yes)): `node <AG>\assets\taste\scripts\assets.mjs "<search>"` queries Openverse, Wikimedia Commons, Art Institute and Met without a key, only with a license that allows commercial use; `--get` downloads and records the license. The file goes to `Banco de Imagens\` with source and license in `historico.md` (`operations.md` §6) and is never presented as the client's photo. Without network, draw it or ask for the input.
8. **App screen** (dashboard, panel, settings): `references\taste\app-screens.md` and `draw.mjs --app`.
Support on demand: `references\taste\type.md`, `colour.md`, `layout.md`, `imagery.md`. Taste's house rules (no gradient, shadow at rest, monospace, eyebrow, numbering, thin line) are not adopted as rules; they count as signals of `quality.md` §A, because the KV and the idea decide. Review: gaze script of `quality.md` §H (passes 1, 2, 4, 9 and 11 in the deck) over the screenshots; the transition between slides follows the gate of `quality.md` §C (presentation is a rare moment).

## 4. Create a new LP or site (P1)
### Structure of an LP that converts
The **text** is always the approved copy (Law 4): if the briefing does not bring a section's text, ask for it, never invent. Reference scroll order (adjust to traffic temperature: cold = longer, with education and proof; hot = shorter, with offer and early CTA):
1. **Hero:** clear promise within 3 to 5 seconds (result + for whom), subtitle, main CTA visible without scrolling on desktop and mobile, and short proof if any.
2. **Problem or pain:** the audience's current scenario. 3. **Solution or mechanism:** what is different in this offer. 4. **Benefits:** written as result ("for you…"), not as feature. 5. **Proof:** real testimonials, confirmed numbers, client logos and confirmed certifications. 6. **Offer and how it works:** steps, what is included and commercial condition. 7. **Objections and FAQ:** price, trust, time, complexity. 8. **Final CTA** + form or button; repeat the CTA every 2 or 3 sections on long pages.
Check: what grabs attention first, the promise or the CTA? Is there a single objective per page? Is there unnecessary friction (too many fields, escape links)?
### Visual direction
- **One strong idea per page**, coming from `design_system.md` (or consulted with `engines\uiux\scripts\search.py "<segment>" --domain brand`). Avoid generic layouts (text on the left and image on the right repeated in every section; hero with only icon and text) without its own treatment.
- **Palette and color scarcity:** the KV colors, with 3 to 5 colors plus the neutrals. The primary accent is surgical (brand, main CTA, focus and highest-priority highlight); never use the accent color as decorative fill for a whole section without provision in the KV.
- **Surfaces and accent:** U4; in dark, the canvas itself is the negative space and sections are separated by elevation. **Spacing:** U5; card padding `24px` (features and pricing), `32px` (testimonials), `48px` (CTA banners). **Radius and shadow** follow the KV (consistent scale per component: chips `4px`, buttons and inputs `6–8px`, cards `12–16px`, pills `9999px`).
- **Images:** order of Law 5. Never deliver with a placeholder (`placehold.co`, `picsum`, lorem). AI-generated images are saved in `IA\`.
- **Microinteractions and state matrix:** define `default`, `:hover`, `:active`, `:focus-visible` and `:disabled` on every interactive element, with transitions of 150 to 300 ms. Animation beyond that: frequency gate and weight by context in `quality.md` §C.
- **Adjustments in the preview (optional):** live adjustment panel only on the workbench, to show variations of color, size or density without opening several files: `assets\preview_adjustments.js` (live adjustment in the preview; plain JS, `window.TWEAKS` with 5 or 6 discrete items, default value is already the complete piece, `localStorage` with `try/catch`). The final file does not carry the script.
- **Final test:** does the page look made to measure for this brand? If it would serve any client by swapping only the logo, iterate.
### Typography
- **Hero:** H1 with `clamp` from ≥ 40 px (375) to ≥ 64 px (1440); main CTA visible without scrolling on both. **Body text:** 16 to 20 px (`clamp(1rem, 0.95rem + 0.3vw, 1.125rem)`), line-height 1.45 to 1.6 and at most `65ch`.
- **Scale, leading and tracking:** U3; sizes with `clamp`, never `vw` alone on text (breaks zoom; the builder's fixed canvas in §6 is a different case). **Families:** U3; `mono` only for code, IDs and tabular data.
- **Properties:** `text-wrap: balance` on titles (semantic break, zero orphan words) and `text-wrap: pretty` on paragraphs; `font-kerning: normal`; table numbers with `font-variant-numeric: tabular-nums`. **Loading:** `preconnect` for `fonts.googleapis` and `gstatic` and `display=swap`; only the weights used; system fallback in the stack.
### Performance (Core Web Vitals: LCP < 2.5 s, CLS < 0.1, INP < 200 ms)
Main hero image with `fetchpriority="high"`, without `loading="lazy"` and with `width` and `height`; the others with `loading="lazy" decoding="async"` and `width`, `height` or `aspect-ratio`; WebP or AVIF when the builder accepts, JPG for photo, SVG for icon, never an image larger than 2× the displayed size; JS at the end of `<body>`, no heavy library for an effect CSS solves; background video with `muted playsinline loop preload="metadata"` and `poster` (on mobile, consider the poster only).
### SEO and sharing
`<html lang="pt-BR">`, a single `<h1>` and headings in hierarchy without skipping a level; `<title>` up to 60 characters (promise + brand) and `meta description` with 150 to 160; `canonical`, `og:title`, `og:description`, `og:image` (1200×630 hosted) and favicon; JSON-LD structured data **only with real information** (`Organization` with name, site and logo; `FAQPage` when there is an FAQ); external links with `rel="noopener"` when they open in a new tab.
### Accessibility (WCAG 2.1 AA)
Contrast and touch targets: U1. Every field with a visible `<label>`, not relying on the placeholder alone, and errors announced with `aria-live`; descriptive `alt` on content images and `alt=""` on decorative ones; "skip to form or content" link, logical tab order, focus always visible and touch targets ≥ 44×44 px on mobile; no information conveyed by color alone.

## 5. Form (P1, P2, P3)
- It does not need to be native to the builder: implement in HTML and JS in the file itself when the page is new. Only the necessary fields: each extra field reduces conversion.
- **BR phone:** mask `(00) 00000-0000` or `(00) 0000-0000`, applied on the `input` event preserving the cursor; `maxlength` over the formatted text and `preventDefault` on keys are forbidden; Backspace, paste and autofill free; validates 10 to 11 digits with area code.
- **UTMs:** `utm_source`, `utm_medium`, `utm_campaign`, `utm_term` and `utm_content` in hidden fields, persisted in `sessionStorage`, plus `page_url`, `referrer` and date and time.
- **Email:** B2B (per `design_system.md` › Inteligência) blocks webmail and validates CNPJ if the field exists; B2C accepts webmail and validates CPF if the field exists. Without Inteligência in the KV: B2B if the copy talks about resale, CNPJ or company; when in doubt, treat as B2C and confirm with the user.
- **Webhook:** `POST` `application/x-www-form-urlencoded` to the URL recorded in `design_system.md` (Inteligência section); without a URL, leave the placeholder and warn. Never invent a URL. In flows with **B2B qualification gates** (one answer disqualifies the lead midway through the form), fire only Analytics or `dataLayer` and the webhook with `qualificacao: "desqualificado"` for the disqualified, reserving the main conversion pixel (`Lead` or MQL) for qualified leads.
- **Mobile-first stability** (`form-validation.css` (form validation style)): (1) always reserve the error message height below each input (`min-height: 16px` on the `.form-msg` created at load), so the layout never jumps on validation; (2) lock the form's maximum height (`max-height: min(88svh, 680px)`) with internal scrolling (`overflow-y: auto; overscroll-behavior: contain`); (3) submit button always visible in a stuck footer (`position: sticky; bottom: 0`); (4) inputs with `min-height: 44px` and `font-size: 16px` (avoids iOS automatic zoom).
- **Behavior:** button locked on submit, success or error message, honeypot, correct `autocomplete` and per-field error. **Errors:** validate on `blur`; 2 or more errors on submit = focus a summary at the top with links to the fields; 1 error = focus the field; `scroll-margin-top` so the fixed header does not cover it.
- **Framing in a box or card (especially on mobile):** when the form sits on a card or frame (own div or absolute background element in builders), never leave inputs and button stuck to the edge or the same width as the box. Centered box and equal inner breathing room on all 4 sides (`24px` on mobile, `32–40px` on desktop; when extracting, the original's breathing room, and in its absence the same values), card header, fields and button at the same usable width, and the card height hugging the button with the same bottom padding. Unify font weight, side arrow and hover of the submit button with the page's other CTAs.
- **Ready-made library (`form-validation.js`):** CPF and CNPJ, state and city cascade (IBGE; API down = free text), MX and disposable email (DNS failed = does not block the lead). Use it, do not reimplement.

## 6. Extract, embed, recreate and tokens (P3)
Copy what is accessible (`operations.md` §6): real HTML, CSS, variables, images and logo, **without redesigning, changing font or color**; only the briefing and the 4 adjustments below are allowed deviations.
### 6.1 Extract and clone: universal optimization of a builder LP (fixed canvas `.gp-page`)
- **1. CTA standardization and alignment:** identify the button with the greatest typographic weight (`font-weight`) and unify all CTAs (`.elemento_botao` links and `.gpc_botao` submit) to that weight, case and leading. Force horizontal layout (`display:flex !important; flex-direction:row !important; flex-wrap:nowrap !important; align-items:center; justify-content:space-between; gap:16px`) so the icon or arrow always sits on the right side inside the button (never pushed down by `flex-direction:column` or `width:100%` on the `span`). If the form button lacks the side arrow of the others, inject it via `::after` with `background:url("data:image/svg+xml,...") center/contain no-repeat` using the same SVG.
- **2. Consistent hover on all CTAs:** builders apply `rgba(0,0,0,0.06)` (imperceptible) on CTA links and a system color (e.g. green `--g-color-success`) on the submit. Replace everyone's `:hover` with an intentional variation of the page's own action color (darken ~15 to 20% keeping the text contrasting and shift the arrow with `transform:translateX(4px)`), without changing the KV.
- **3. Fluid scale between breakpoints and prevention of text cuts:** builder pages use a fixed absolute canvas (e.g. `360px` on mobile and `980px+` with elements at negative coordinates on desktop) and cut text in intermediate windows (801 to 1100 px) or narrow ones (< 360 px). Always: (a) `overflow:visible !important; overflow-wrap:break-word` on the `.conteudo.elemento_texto` boxes; (b) raise the mobile/desktop switch breakpoint if the desktop elements exceed the container width (e.g. from `800px` to `1099px`); (c) fluid proportional scale (`zoom: var(--lp-z, 1)`) on `.block > .center`, recalculating each `.block`'s height via JS (`vw / real_desktop_width` when the screen is smaller than the real width of the desktop layout, and `(vw - 32) / mobile_width` on mobile, for 16 px of symmetric side breathing room on any screen); (d) horizontal strips of topics or badges that overflow on mobile become `display:flex; flex-wrap:wrap; justify-content:center`.
- **4. Framing and breathing room of the form inside the background box:** with a box or border behind the form, it must never be the same width as the box nor spill below it. Center the box in the mobile container (`width:360px; left:0`) and apply symmetric inner padding (the original's; in its absence, `24px` top, bottom and sides), adjusting `left` (`24px`) and `width` (`calc(box_width - 48px)`, e.g. `312px`) of the `<form>` and the card's header texts, and resizing the background box's height and the section block's height to fit all the fields and the button with the same bottom breathing room, repositioning what comes below.
### 6.2 Embed: components for `</>` blocks
When the user asks to split an LP into embeds for builders' `</>` blocks:
1. **Classification matrix (`🟢 Extract` · `🟡 Case by case` · `🔴 Native`):** **🟢 always extract (11 rules, 0 to 10):** (0) form with B2B/B2C validation, UTMs, first/last-touch and event firing; (1) JS with logic or calculation (PMT, simulator, sliders with dynamic lock, custom countdown); (2) decorative absolute pseudo-elements (`::before` and `::after` connecting steps or timelines); (3) gradient text (`-webkit-background-clip: text`); (4) comparison tables with custom colored cells or columns; (5) modal or overlay; (6) conditional animation (accordion with `max-height`, `+` icon rotating to `×`); (7) card with absolute floating badge or tag (`-top-3`) or rotated stickers; (8) exclusive accordion (opening one closes the others); (9) sophisticated hover (`transform: translateY`, `::before` glow or joint border and shadow change); (10) glassmorphism (`backdrop-filter: blur`). **🔴 Keep native in the builder:** simple hero without gradient text, simple stats, basic cards without complex hover, static navbar, footer and simple lists. Present the classified list in 1 line per item and confirm which to extract (default: all 🟢) in `embeds-{nome}/`.
2. **Inviolable technical isolation of each embed:** `body { background: transparent; margin: 0; }` (never a background color on the embed body); **100% scoped CSS** in the `.{componente}-wrap` namespace (including CSS variables defined in `.{componente}-wrap`, **never** in `:root`, and scoped box-sizing), converting any external utility class to standalone plain CSS; **JS in an IIFE** (`(function(){ 'use strict'; ... })();`), prefixed IDs (`embed-...`), functions with a short prefix and `IntersectionObserver` restricted to its own wrapper; **modal:** on init, move the modal to `document.body.appendChild(modal)` to escape the builder's parent containers that apply `transform` or `filter` and break `position: fixed`.
3. **Full-bleed marquee (edge to edge):** `</>` blocks are stuck to the column width and `100vw + calc(50% - 50vw)` generates asymmetric overflow on mobile. Detect by `100vw`, 100% width at the top or bottom of the section, `@keyframes translateX` or an "edge to edge" request, and also generate `_LP-LEVEL-CODE-marquees.html` for the page's code panel: hide the original block keeping the box in the DOM (`.e_XXXXX_BLOCO { visibility: hidden !important; }`, only with `visibility:hidden`, because the builder's desktop/mobile toggle removes it from the DOM and breaks the JS), reserve the height in the parent section (`#b_XXXXX_SECAO { min-height: 90px; }`) and inject the `.marquee-fb` strip directly into `document.body` with `position: absolute; left: 0; width: 100vw`, syncing `top` and `height` via `getBoundingClientRect() + window.pageYOffset` in `ResizeObserver`, `scroll`, `resize` and timeouts (`200, 600, 1500, 3000, 6000 ms`). Remember: `#b_xxx` = section ID (parent and anchor); `.e_xxx` = HTML block class (child to hide).
4. **Builder that removes inline `<script>`** (test in the published preview): host the component as a standalone page and embed it via `<iframe>`.
### 6.3 Recreate from a screenshot or video
- **Total fidelity to the screenshot:** same colors, sizes, spacing, fonts and texts, with the **exact** text of the image. Images in the screenshot: extract the croppable ones; those that cannot be extracted come from `Compartilhada\Imagens\` or are AI-generated (saved in `IA\`). Never use the whole screenshot as image or background, only croppable assets; pixelated asset = upscale (`image.md` Part A §1), never stretch via CSS.
- **Several screenshots:** different pages become pages linked to each other; without a relation, separate into "Print 1", "Print 2" sections. **Phone screenshot:** no device frame or browser bar.
- **Video:** recreate the behavior so the same interactions produce the same result; watch color, font, padding, margin and border; mock data when there is a backend; make it functional with JS.
- **Verification:** render on desktop and mobile and compare side by side with the screenshot; fix until identical. Element pointed at in the builder: the live DOM may have injected classes; locate by tag + id + class + text and change only it.
### 6.4 Tokens and design language of a site (designlang, MIT)
When the request is "extract the design system", "what colors and fonts does this site use", tokens, Tailwind theme or Figma variables of a live site. It is not for cloning the page (that is §6.1). `operations.md` §6 applies: what is extracted is reference (color, typography, scale, motion), never a third party's logo, text, photo or literal layout.
- **Built-in engine:** `engines\designlang\`. First time: `npm install --omit=dev` inside that folder, only with the one-time dependencies approval (`operations.md` §0.6); without the approval, the flow falls back to the DOM and computed CSS of §6.1.
- **Usage:** `node <AG>\engines\designlang\bin\design-extract.js <url> --out <folder>\Trabalho\tokens [--dark] [--depth N] [--screenshots]`. Outputs: `*-design-language.md` (reading for AI), HTML preview, W3C/DTCG tokens, `tailwind.config.js`, CSS variables, shadcn theme, Figma variables, WCAG note. Also `diff <urlA> <urlB>` (comparison), `theme-swap <url> --primary "#hex"` (recolor in OKLCH) and `brand <url>` (13-chapter brand book).
- **Do not use:** `--smart`, `chat`, `sync`, `ci`, `pack` and the gallery routines: they call external APIs (OpenAI, Anthropic, another provider) that require a key, and a key never goes into the chat (`operations.md` §6). What the engine prints about `designlang.app` is the author's promotion, not delivered capability.
- **Result in the flow:** the `*-design-language.md` feeds `kv-logo.md` Part A §2 (new client) and Part C (`DESIGN.md` and `tokens.css`); the client's approved KV remains in charge (U11).

## 7. Report page and dashboard (P4)
- **Decision order (inviolable: never write content before locking steps 1 to 4):**
  1. **Page mode (`Page Mode`):** audience, context and narrative before the HTML: `summary-to-detail` (inventories and status), `chronological` (roadmaps and migrations), `problem-to-solution` (proposals), `capability-map` (architecture and platform), `comparison` (matrices and before and after), `layered-architecture` (physical, logical and operational views).
  2. **Chapter flow (`Chapter Flow`):** group the material into sections with 1 clear mission each; in long documents (> 5,000 words), build the chapter plan before drafting.
  3. **Dominant visual pattern per chapter:** 1 per section: grid of 4 to 5 summary cards with balanced text volume, 3-column architecture diagram (`left context → center detail → right context` with `align-items: stretch`, equal widths, same height per row, h3 on 1 line), comparison matrix, timeline, risk register or dense table.
  4. **Semantic color mapping, locked once on the page:** the same color always means the same category in all sections (e.g. blue = production or asset; green = shared or completed; orange = in progress or asynchronous; purple = external service; yellow = persistence or data; red = risk or alert). **Color is category, never priority:** priority uses an explicit label (`P0`, `P1`).
  5. **Content filling:** compact, scannable and 100% self-contained (opens offline).
- **Components and responsiveness:** lean hero (eyebrow, title, subtitle of up to 2 sentences and 4 to 6 numeric status metrics); `sticky` horizontal navigation (mandatory from 4 sections); uniform vertical spacing between sections (`20–24px`); below `980px` 4-column grids become 2, below `640px` 1 column; `@media print` hides the navigation, removes shadows and applies `break-inside: avoid`.
- **Content:** open with the result, current state or requested decision; label with a business name (technical ID only as secondary text); each item appears in 1 place only. **Status:** distinguish deployed, in progress and planned; never "in production" without a source. **Cards:** up to 3 lines; more than 6 of the same type = group or table; pill only when functional (the source text said "plans, pill only functional").
- **Charts (inline SVG, never a library via CDN):** trend = line; comparison = bar (3 to 12 categories); proportion = donut only up to 5 categories; direct label with unit, never color alone; data with contrast ≥ 3:1 against the background.
- **Final verification:** opens offline, prints to PDF without cuts and the navigation links lead to the right sections.

## 8. Deck: presentations and visual narratives (P5)
Separate the **iterable workbench** from the final file. Pixel-perfect HTML/CSS/JS (1600×900 canvas, single file, no framework or build) is the authoring and delivery standard; PowerPoint, PDF or a native format come in when the user asks or the use requires it, without swapping the standard silently.
### 8.1 Workbench and canvas
- **Choice guided by use:** identify audience, presentation context, available content, final destination, need for editing, collaboration, printing and environment capability. Do not turn the name "deck" into predetermined HTML, PPTX, aspect ratio, slide count or layout; the workbench may be independent of the exported file.
- **Preview in the Browser** when available: open a visual canvas with the piece in progress and adjust HTML, CSS and JS while iterating. The `16:9` canvas serves widescreen slides; use a provisional dimension when there is uncertainty and do not confuse the preview canvas with the final slide. A 1600×900 deck scales to the viewport:
```css
html, body { margin: 0; padding: 0; width: 100%; height: 100%; overflow: hidden; }
#viewport { position: fixed; inset: 0; overflow: hidden; }
#deck { position: absolute; width: 1600px; height: 900px; left: 50%; top: 50%;
  transform: translate(-50%, -50%) scale(var(--deck-scale, 1)); transform-origin: center center; }
```
```js
function fitDeck() {
  var vw = (window.visualViewport && window.visualViewport.width) || document.documentElement.clientWidth || window.innerWidth;
  var vh = (window.visualViewport && window.visualViewport.height) || document.documentElement.clientHeight || window.innerHeight;
  var scale = Math.max(0.1, Math.min((vw - 16) / 1600, (vh - 16) / 900, 1));
  document.getElementById('deck').style.setProperty('--deck-scale', scale);
}
window.addEventListener('resize', fitDeck);
if (window.visualViewport) window.visualViewport.addEventListener('resize', fitDeck);
fitDeck();
```
- **Dimensions and safety:** use the client's template and tokens only when approved and relevant; otherwise define canvas and margins by aspect ratio, content type, display environment and destination requirements. Never confuse metadata DPI with final physical resolution; for printing, confirm trim, bleed, scale, profile and proof with the printer.
- **Typography and breathing room:** by narrative hierarchy, real presentation size, distance and tokens; never shrink the type just to force content onto a slide (too much content = split or change archetype). The 1600×900 measurements (`h2 ≥ 44px`, `h3 ≥ 20px`, body `≥ 17px`) are a reference for that canvas, not a universal floor.
### 8.2 Archetypes and cadence (repertoire, not mandatory mapping)
| Content signal | Structures that may serve |
|---|---|
| 1 decisive impact statement | **Statement / Hero:** 1 dominant sentence + 1 abstract or geometric system from the KV |
| 4 capabilities or pillars | **2×2 grid** of cards with icons |
| 5 capabilities or pillars | **Asymmetric grid:** 2×2 + 1 highlighted vertical card on the right |
| 6 capabilities or pillars | **3×2 grid** of cards with icons |
| Before × After | **Split Flow:** 2 large panels with directional flow |
| Old scenario × New solution | **Comparison:** 2-column table with generous height or side-by-side contrast |
| Sequential steps (up to 6) | **Process / Timeline:** connected horizontal steps (or 2 rows if > 6), equal heights, icon per step and highlight on the final result |
| Central intelligence + units | **Hub & Network:** central radial circle + dashed orbit + nodes with explicit positional classes (`node-nw`, `node-ne`, `node-sw`, `node-se`, `node-s`; never `:nth-child` when there are non-node siblings) and asynchronous floating (`node-float` with distinct negative delays) |
| Metrics and numbers (up to 5) | **Metric Wall:** giant digits (`big-number`), 1 highlighted result and confirmed period caption |
| 1 dominant metric + activities | **Allocation Ring:** dominant animated ring + grid of bullets with icons |
| Operational indicators | **Dashboard mockup** in the product's or KV's style |
| Price and commercial condition | **Price Card** + side panel of conditions and deliverables |
- **Rhythm:** contrast of composition, density, scale and background can create cadence; choose by the material and the visual language, with no mandatory number of treatments and no limit on identical slides. **Argument before layout:** §3 (list the deck as claims, one per slide with the proof, and cut the slide without a claim). **Data:** only turn into a chart what is authorized, via §7 when it is a report. **Space:** empty areas, breathing room and asymmetric compositions are legitimate choices; do not enlarge cards just to eliminate space.
### 8.3 Content guardrails
1. **Literal copy and allowed transformations:** use exclusively the facts, numbers and arguments provided. It is allowed to break long sentences into parallel blocks, turn lists into cards with icons and convert pairs into comparison tables, keeping 100% of the original concepts. It is **forbidden** to invent explanatory subtitles, name methodologies not cited, infer numbers, axes or periods, or create generic final CTAs that are not in the copy.
2. **Editorial finish (when it makes a difference):** adjust breaks, orphans, contrast, spacing, density and hierarchy for the medium and the audience. Hyphen, dash, emoji, bullets, list without icons, long paragraph or metalanguage are not automatic failures; fix when they weaken reading, tone or intent. Do not fail for style preference or the lack of an archetype.
### 8.4 Iterate, approve and export
- Present the composition in the Browser canvas when available; otherwise, the medium's viable visual representation. Receive feedback and edit the workbench without requiring an exported file at each iteration. Content, claims, numbers, source and brand remain faithful to the briefing.
- After approval, confirm the final format, dimension, compatibility and destination not yet defined, and **export only the chosen formats**; an image from the workbench is not the final PPTX or PDF.
- **PPTX, one route per situation:** (a) **derived from the finished HTML (default, the HTML remains the source and primary delivery):** `python -I -X utf8 <AG>\assets\huashu\pptx_from_rendered.py deck.html -o deck.pptx --selector ".slide"` (huashu-design, MIT). Reads the already rendered positions, so it does not ask to rewrite the HTML: text becomes an editable box, card becomes a shape, SVG and canvas become an image, and the lost-text check runs by itself. Uses Playwright, python-pptx and Pillow; `-X utf8` avoids console errors on Windows; the 1600×900 canvas comes out at 22.2×12.5 in (1 px = 1 pt); with a client template: `--template modelo.pptx --layout "<name>" --skip-class logo` (the logo comes from the layout). Details and text pitfalls: `references\huashu\pptx-from-rendered-html.md`; the route that requires rewriting the HTML with 4 restrictions (no gradient, no background on text) contradicts pixel-perfect and is not included. (b) **Native PPTX with `python-pptx`:** only when the PPTX is the authoring (the user chose PPTX, or editability and interoperability require it); create native elements whenever possible.
- **PDF** is an export, not an editable source, and only after format and quality are defined. **Native Figma** only when requested, via the `figma.md` route. **Printing:** exact requirements of the organizer or the printer; a missing requirement is a question after approval, not a reason to invent dimensions, bleed, DPI, color or certificate.
- If the format is PPTX, verify opening, slide count, dimensions, text, local assets and shape bounds; structural validation does not prove visual fidelity: **render and review in PowerPoint or the available exporter before delivering** (`quality.md` §K); without a converter, declare it and do not claim a render review took place.
### 8.5 Interaction and QA of the HTML preview
- **Navigation and accessibility:** previous and next buttons (`data-testid="prev-slide"` and `data-testid="next-slide"`, disabled on the first and last slide), keyboard arrows (`ArrowLeft` and `ArrowRight`), `Space` and `PageDown`, `Home` and `End`, touch swipe ≥ 50 px, `.progress-fill` bar reaching 100% on the last slide, updated counter and `@media (prefers-reduced-motion: reduce)` disabling continuous animations. Confirm navigation and controls only if implemented and relevant.
- `check_deck.py` assumes specific HTML and slide conventions: run it when the file fits that contract, explain valid warnings for the piece and do not impose dash, icon on every list, rotating backgrounds or maximum words as a general design rule. Review contrast, overflow, fonts, interactions, metadata and console according to the content and use; outside HTML, use the corresponding validation if one exists.
